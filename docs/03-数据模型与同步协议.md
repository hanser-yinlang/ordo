## 2. 规范数据模型

所有实体字段名在**四端与后端完全一致**(JSON 即传输格式,也是本地库字段名)。时间戳统一 `epoch millis (Int64)`;日期用 `YYYY-MM-DD`;日期时间用 `YYYY-MM-DDTHH:mm`(本地时区,不带秒)。

```
When = "inbox" | "today" | "evening" | "anytime" | "someday" | "date"
Status = "open" | "done" | "canceled"
RepeatFreq = "daily" | "weekly" | "monthly" | "yearly"
RepeatMode = "fixed" | "afterCompletion"
```

### 2.1 Area
```jsonc
{ "id":"uuid", "name":"工作", "color":"#5B5BD6", "order":0, "archived":false,
  "updatedAt":1759900000000, "deleted":false }
```

### 2.2 Project
```jsonc
{ "id":"uuid", "areaId":"uuid|null", "name":"Q4 产品发布", "note":"markdown",
  "when":When, "date":"YYYY-MM-DD|null", "deadline":"YYYY-MM-DD|null",
  "tags":["重要"], "order":0,
  "status":Status, "completedAt":null, "repeat":RepeatRule|null,
  "createdAt":1759900000000, "updatedAt":1759900000000, "deleted":false }
```
> **实现说明(避免歧义)**:标题(Heading)是**顶层实体**,单独存储与同步(见 §2.3 与 §7.4 的 `headings` 数组);
> 项目的"标题列表"是**派生的视图**(按 `heading.projectId == project.id` 查询并按 `order` 排序),不内嵌在 Project 里。
**项目完成规则(硬约束)**:仅当该项目下所有 todo 的 status ∈ {done, canceled} 时才允许 `status="done"`。
> **v1.1 修订(2026-10-09)**:原规则还要求「所有 heading.archived == true」,该要求已**删除**。
> 原因:Heading 是**组织容器**不是工作项,要求用户先把每个标题逐个归档才能完成项目,与用户预期不符 ——
> 实测中"项目显示 0 项未完成、进度 100%,点完成却被拒绝"即由此产生(四端都会出现同样的困惑)。
> 现改为:**完成项目时,该项目下未归档的 heading 由引擎自动归档**(每个标题产生一条对应 Op,与手工归档同构),
> 因此「已完成的项目不含未归档标题」这一不变量仍然成立,只是不再需要用户手动操作。

### 2.3 Heading
```jsonc
{ "id":"uuid", "projectId":"uuid", "name":"设计", "order":0,
  "archived":false, "collapsed":false, "updatedAt":..., "deleted":false }
```
`collapsed` 是**设备本地 UI 状态**,不参与同步(推送时置 null,服务端忽略)。
> 所有实体(含 Heading 与 Tag)都带 `deleted` 字段:§3 的"删除一律软删除"对其同样适用。
> 删除时客户端同时登记本地墓碑,并发送 `type="delete"`(payload 为 null)的 Op;接收侧对 `type=delete`
> 与 `payload.deleted=true` 两种形态都必须正确处理(兼容不同实现)。

### 2.4 Todo
```jsonc
{ "id":"uuid", "title":"交季度报告", "note":"markdown",
  "when":When, "date":"YYYY-MM-DD|null", "reminder":"YYYY-MM-DDTHH:mm|null",
  "deadline":"YYYY-MM-DD|null",
  "tags":["重要"], "checklist":[ChecklistItem],
  "projectId":"uuid|null", "areaId":"uuid|null", "headingId":"uuid|null",
  "repeat":RepeatRule|null, "order":0, "status":Status,
  "createdAt":..., "updatedAt":..., "completedAt":null, "deleted":false }
```

### 2.5 ChecklistItem(内嵌,不单独同步)
```jsonc
{ "id":"uuid", "title":"订机票", "done":false }
```

### 2.6 Tag
```jsonc
{ "id":"uuid", "name":"重要", "color":"#FF6B5A", "updatedAt":..., "deleted":false }
```

### 2.7 RepeatRule
```jsonc
{ "freq":"weekly", "interval":1, "mode":"fixed" }
```
- `fixed`:下一次日期基于**原 date** 递推(每周一永远是周一)。
- `afterCompletion`:下一次日期基于**实际完成日**递推。

### 2.8 CalendarEvent(只读,设备本地,不同步)
```jsonc
{ "id":"local", "title":"产品评审会", "start":..., "end":..., "calendar":"工作", "allDay":false }
```

## 3. 字段默认值与不变量

| 规则 | 说明 |
|---|---|
| 新建待办未指定 `when` 且未指定 `projectId` | `when="inbox"` |
| 新建待办未指定 `when` 但指定了 `projectId` | `when="anytime"` |
| 待办被移入项目时 `when=="inbox"` | 自动改为 `"anytime"`(否则会同时留在收件箱) |
| `when=="date"` | `date` 必须非空;`date` 为空时补今天 |
| `when ∈ {inbox, today, evening, anytime, someday}` | `date` 必须为 null |
| `reminder` 非空 | 其日期部分必须等于 `(when=="date" ? date : 今天)`;客户端设置时自动对齐。**因此修改 `date` 会平移提醒到新日期的同一时刻**(重复实例同样平移),这是明确预期行为 |
| 设置 `reminder` 且 `when ∈ {inbox, anytime, someday}` | 自动改为 `"today"`(对应 Things 的"带提醒即进今天") |
| `headingId` 非空 | 必须属于 `projectId` 指向的项目;否则置 null |
| 标题为空字符串的实体 | 视为删除 |
| 删除 | 一律**软删除**:`deleted=true` + `updatedAt` 更新;服务端保留墓碑 30 天 |

## 4. 派生清单查询规范(四端必须逐条一致)

> 所有清单都是查询,不落库。`E` = `deleted != true` 的实体全集;`open(t)` = `t.status == "open"`。

| 清单 | 精确规则 |
|---|---|
| 收件箱 Inbox | `open(t) && t.when == "inbox"` |
| 今天 Today | `open(t) && (t.when in {today, evening} \|\| (t.when=="date" && t.date <= today) \|\| (t.deadline != null && t.deadline <= today))` |
| └ 今晚分区 | 上述结果中 `t.when == "evening"` 的单独一组,置于底部 |
| └ 逾期标记 | `t.deadline != null && t.deadline < today` → 珊瑚红 |
| 计划 Upcoming | 窗口 = 明天起 14 天。含:`t.when=="date" && t.date ∈ 窗口`、`t.deadline ∈ 窗口`、`repeat != null` 的下一次发生日 ∈ 窗口;按天分组,超出窗口归入「更晚」 |
| 随时 Anytime | `open(t) && t.when == "anytime"`,按 project → area 分组 |
| 某天 Someday | `open(t) && t.when == "someday"` |
| 日志簿 Logbook | `t.status in {done, canceled}`,按 `completedAt` 的日期倒序分组 |
| 项目视图 | `t.projectId == P.id && open(t)`,先按 `heading.order` 分组(`headingId == null` 的排在最后),组内按 `t.order` |
| 区域视图 | `t.areaId == A.id \|\| project.areaId == A.id` |
| 标签视图 | `t.tags.contains(name)`,可切换"只看未完成" |
| 搜索 | 标题或备注包含关键词(大小写不敏感);结果排序:未完成优先 → `updatedAt` 倒序 |
| 项目进度 | `done / (done + open)`;无子项时 0 |

## 5. 中文自然语言解析规范(NLP v1)

输入示例:`明天 18:00 交季度报告 #重要`

**输出**:`{ cleanTitle, when, date, reminder, tags }`

| 类别 | 支持写法 | 结果 |
|---|---|---|
| 今天 | 今天 / 今日 | `when=today` |
| 今晚 | 今晚 / 今天晚上 | `when=evening` |
| 相对天 | 明天 / 明日(+1)、后天(+2)、大后天(+3)、N天后 | `when=date, date=…` |
| 相对周 | N周后 / N个星期后 | `when=date` |
| 相对月 | N个月后 | `when=date` |
| 绝对日期 | `2026-10-09`、`10月9日`、`10月9号`、`10/9` | `when=date` |
| 星期 | 周五 / 星期五 / 礼拜五、下周五、下下周三 | 本周内未过则本周,否则下周;带"下"按指定周偏移 |
| 周末 | 周末 / 本周末 / 这个周末 | 最近的周六 |
| 暂缓 | 某天 / 将来某天 / 有空再说 | `when=someday` |
| 时间 | `18:00`、`18点`、`18点半`、`下午3点半`、`晚上8点`、`8pm` | 生成 `reminder`(日期取解析出的 date,否则今天);无日期信息时 `when=today` |
| 标签 | `#重要`(可多个) | 追加到 `tags`;标签必须已存在,否则自动创建 |
| 清理 | 上述片段从标题中移除,压缩多余空格与首尾标点 | `cleanTitle` |

**冲突优先级**:绝对日期 > 相对月 > 相对周 > 相对天 > 关键词(今晚 > 今天/明天…)> 时间。
**时段换算**:上午/早上 保持;中午 → 12 点;下午/傍晚/晚上/夜里 → +12(仅当 <12);凌晨 12 点 → 0 点。

## 6. 重复规则引擎

完成一个 `repeat != null` 的待办时:

1. 原实例:`status=done`、`completedAt=now`、`repeat` 保留(用于日志簿展示"曾重复")。
2. 生成新实例:复制全部字段,`id` 重新生成,`status=open`、`completedAt=null`、`checklist[].done=false`、`createdAt=now`。
3. 新 `date`:
   - `mode=fixed` → `base = 原 date ?? 原 reminder 的日期 ?? 今天`
   - `mode=afterCompletion` → `base = 今天`
   - `freq=daily` → base + interval 天;`weekly` → +7×interval 天;`monthly` → 月份 +interval(日期溢出取当月最后一天);`yearly` → 年份 +interval。

## 7. 同步协议 v1

### 7.1 总体模型

- **本地优先**:所有写操作先落本地库,立即返回 UI,再由同步引擎异步推送。
- 每个写操作产出一条 **Op**,进入本地 `outbox`(持久化队列)。
- 客户端维护 `lastServerSeq`;服务端为每个用户维护单调递增 `serverSeq`。
- **幂等**:`opId` 全局唯一(ULID),服务端以 `op_id` 唯一索引去重,重复推送直接返回 accepted。
- **两项通道**:常规批量同步(HTTP)+ 实时推送(WebSocket);提醒另走 **Fastlane** 优先队列。

### 7.2 Op 结构

```jsonc
{
  "opId":"01JABCDEF...",        // ULID,客户端生成,幂等键
  "deviceId":"dev_7f3a...",
  "entity":"todo|project|area|heading|tag",
  "entityId":"uuid",
  "type":"upsert|delete",
  "payload":{ /* 实体完整快照;delete 时为 null */ },
  "clientTs":1759900000123,     // 客户端时钟(epoch millis),LWW 依据
  "seq":128                     // 仅服务端下发时有;上传时省略
}
```

### 7.3 冲突合并规则(四端与服务端必须一致)

1. **实体级 LWW**:比较 `clientTs` 与本地 `updatedAt`;`clientTs >= updatedAt` 才应用,否则标记 `stale` 并丢弃。
2. **完成不可回滚**:若本地 `status ∈ {done, canceled}` 而远端 op 是更早的 `open`,忽略该 op。
3. **标签取并集**:无论 LWW 结果如何,`tags` 取双方并集(删除标签走实体 op,不靠数组差集)。
4. **清单项合并**:按 `checklist[].id` 合并;两端都有的项按所在 todo 的 LWW 结果取一方;仅一端有的项保留。
5. **删除墓碑**:`type=delete` 生成墓碑 `{entity, entityId, deletedAt, clientTs}`,保留 30 天;本地维护墓碑集合,防止旧 op 让实体"复活"。
6. **标题为空**视为删除(与 §3 一致)。

### 7.4 HTTP 接口

基础路径 `/v1`,除 `/auth/*` 与 `/health` 外均需 `Authorization: Bearer <accessToken>`。
统一请求头:`X-Ordo-Schema: 1`、`X-Ordo-Device: <deviceId>`、`X-Ordo-Client: android/1.0.0`。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/v1/health` | `{status:"ok", version, serverTime}` |
| POST | `/v1/auth/register` | `{email,password,deviceName,platform}` → `{user,device,accessToken,refreshToken,expiresIn}` |
| POST | `/v1/auth/login` | 同上 |
| POST | `/v1/auth/refresh` | `{refreshToken}` → `{accessToken,refreshToken,expiresIn}`(旧 refresh 轮换失效) |
| POST | `/v1/auth/logout` | `{refreshToken}` → `204` |
| GET | `/v1/sync/snapshot` | → `{serverSeq,areas,projects,headings,todos,tags}` |
| POST | `/v1/sync/push` | `{deviceId,sinceSeq,ops[]}` → `{serverSeq,accepted[],rejected[],ops[]}`(捎带拉取) |
| GET | `/v1/sync/pull?sinceSeq=&limit=` | → `{serverSeq,ops[],hasMore}` |
| POST | `/v1/devices/register` | 更新设备名/平台/最后在线 |
| WS | `/v1/ws?token=<accessToken>` | 实时通道 |

**限制**:单次 push ≤ 500 ops;单 op payload ≤ 256 KB;pull `limit` ≤ 1000;写接口 ≤ 10 req/s(超限 `RATE_LIMITED`)。

**错误模型**
```jsonc
{ "error": { "code":"AUTH_REQUIRED", "message":"需要登录", "details":{} } }
```
错误码:`VALIDATION_FAILED`、`AUTH_REQUIRED`、`AUTH_INVALID_CREDENTIALS`、`AUTH_TOKEN_EXPIRED`、`AUTH_EMAIL_TAKEN`、`SYNC_SEQ_GAP`、`SYNC_OP_TOO_LARGE`、`NOT_FOUND`、`RATE_LIMITED`、`INTERNAL`。

**401 处理**:客户端遇 `AUTH_TOKEN_EXPIRED` 自动 refresh 并重放原请求一次;refresh 也失败 → 转登录态但**保留本地数据**。

### 7.5 WebSocket 消息

服务端 → 客户端:
```jsonc
{ "type":"hello", "serverSeq":128, "serverTime":1759900000000 }
{ "type":"ops", "serverSeq":130, "ops":[ /* Op[] */ ] }
{ "type":"reminder", "todoId":"uuid", "title":"交季度报告", "at":"2026-10-09T18:00" }   // Fastlane
{ "type":"ping", "t":1759900000000 }
```
客户端 → 服务端:
```jsonc
{ "type":"subscribe", "deviceId":"dev_..." }
{ "type":"ack", "serverSeq":130 }
{ "type":"pong" }
```

**Fastlane 规范**:服务端为 `reminder` 建独立索引,后台每 1 秒扫描"未来 60 秒内到期"的提醒,命中即刻通过 WS 下发(不等待批量合并);同一提醒只投递一次(`fired=true`)。

### 7.6 账号、会话与游客(v1.2 新增)

**产品要求**:启动 App 必须先经过登录页;可以选「游客登录」;数据按用户保存在云端。

#### 7.6.1 身份模型

| 概念 | 说明 |
|---|---|
| `user` | 账号主体。`email` 可为 `null`(**游客**),`isGuest` 标记是否为游客账号 |
| `session` | 本地保存的登录态:`{ userId, email?, isGuest, accessToken, refreshToken, expiresAt }`,存于本地 `kv["ordo.session"]` |
| `deviceId` | 仍然由客户端生成(§7.2 的 `dev_<不透明串>`),同一账号可有多台设备 |

**游客不是"离线模式"**:游客同样向服务端注册一个匿名账号并拿到正常令牌,**数据同样入库、同样多端同步**。区别只有两点:没有邮箱口令、`isGuest=true`。

#### 7.6.2 接口

| 方法 | 路径 | 请求 | 响应 |
|---|---|---|---|
| POST | `/v1/auth/guest` | `{deviceId?, deviceName?, platform?}` | 与 register/login 同构:`{user:{id,email,isGuest}, device, accessToken, refreshToken, expiresIn}` |
| POST | `/v1/auth/upgrade` | `{email, password}`(需带 Access Token) | 把游客账号升级为正式账号:**userId 不变、数据不变**,返回 `{user:{id,email,isGuest:false}}` |
| POST | `/v1/auth/register` / `login` / `refresh` / `logout` | 同 v1 | 响应增加 `user.isGuest`(正式账号为 `false`) |

**错误**:`upgrade` 遇到邮箱已占用返回 `AUTH_EMAIL_TAKEN`;游客账号调用 `login` 返回 `AUTH_INVALID_CREDENTIALS`(无口令可校验),客户端应引导其用原 `refreshToken` 恢复会话或重新走游客登录。

#### 7.6.3 本地数据按用户隔离(硬约束)

- 客户端本地数据目录必须**按 userId 分目录**:`<应用私有目录>/<userId>/`。各端映射:

  | 端 | 应用私有目录 | 账号数据落在 |
  |---|---|---|
  | Windows | `%APPDATA%\Ordo\` | `%APPDATA%\Ordo\<userId>\` |
  | Android | `filesDir/` | `filesDir/<userId>/` |
  | iOS | `Application Support/Ordo/` | `Application Support/Ordo/<userId>/` |
  | 鸿蒙 | ArkData 只允许关系库落在 `<context.databaseDir>/rdb/` | `<databaseDir>/rdb/<userId>/ordo.db` |

- **绝不允许两个账号共用同一份本地数据目录** —— 否则 A 的待办会出现在 B 的界面里。
- **唯一的例外:会话文件本身**。会话必须能在"还不知道 userId"时被读到,所以它固定放在**应用私有目录根部**(如 iOS `Application Support/Ordo/session.json`、Android `filesDir/ordo-bootstrap.db` 的 kv)。键名统一用核心常量 `OrdoSessionStore.KEY_SESSION`(值 `"ordo.session"`);**实体数据一律不得放在根部**。
- 目录名一律经 `OrdoSessionStore.userDataDirName()` 清洗后使用(只保留字母数字与 `-` `_`;清洗后为空则退化为 `_`,绝不返回空串)。
- 退出登录只清除 `session`,**保留**该 userId 目录;下次同一账号登录时数据仍在(离线可用,联网后增量同步)。
- 首次登录某账号且服务端无数据时,才写入演示数据(与 §4 的既有规则一致)。

#### 7.6.4 启动流程(四端一致)

```
启动 → 读 session
  ├─ 有且未过期            → 直接进入主界面(后台静默 refresh)
  ├─ 有但 accessToken 过期 → 先 refresh:
  │       ├─ 服务端返回 401 / 令牌失效 → 回登录页(**只清会话,保留该 userId 目录**)
  │       └─ 网络不可达 / 超时 / 限流   → **留在主界面离线可用**
  └─ 无                    → 登录页(必须选择:登录 / 注册 / 游客登录)
登录页三个入口都要有,游客登录与正式登录体验对等(都能同步)。
```

> **为什么要区分这两类失败**:§7.6.3 要求"退出登录保留目录、离线可用"。
> 若把网络故障也当作登录失效,用户在断网时一启动就被踢回登录页 —— 这正是本契约要避免的行为。
> **只有服务端明确否认令牌(401)才算会话失效**;网络类错误一律按"暂时同步不上"处理,
> 界面显示离线/失败态(见 UI 规范 §5.3),联网后自动续期重试。

## 8. 存储与迁移

- **服务端(PostgreSQL)**
  `users` / `devices` / `refresh_tokens` / `entities(user_id, entity, entity_id, payload jsonb, updated_at, deleted, server_seq)` / `ops(server_seq bigserial, op_id unique, …)` / `reminders(user_id, todo_id, at, title, fired)`。
  索引:`ops(user_id, server_seq)`、`entities(user_id, entity, entity_id)` 唯一、`reminders(user_id, at) where fired=false`。
  无 Postgres 时自动降级为**内存仓储**(同一接口),用于本地开发与自动化测试。
- **客户端**:Android Room / iOS SwiftData / 鸿蒙 RelationalStore / Windows SQLDelight(或 JSON 文件仓储)。**表字段名与 §2 完全一致**;
  另加本地表:`outbox(opId PK, payload, createdAt)`、`tombstones(entity, entityId, deletedAt)`、`kv(key, value)`(存 `lastServerSeq`、tokens、deviceId)。
- **迁移**:`kv.schemaVersion`;升级时按版本号顺序执行迁移脚本;服务端通过 `X-Ordo-Schema` 拒绝不兼容客户端(返回 `VALIDATION_FAILED` 并提示升级)。

## 9. 安全与合规

- 传输:HTTPS/WSS;生产强制 TLS 1.2+。
- 口令:`argon2id`(默认)哈希;最小长度 8,禁止明文与日志落库。
- 令牌:access = JWT HS256(30 min);refresh = 256-bit 随机串,服务端仅存 SHA-256 哈希,30 天,轮换失效。
- 数据:服务端静态加密由数据库/磁盘层负责;`payload` 不含口令。
- 隐私:不采集通讯录/位置;日历事件仅本地读取,不上传;提供"删除账号与全部数据"接口(级联删除)。
- 日志:不打印 token、口令、备注正文。
