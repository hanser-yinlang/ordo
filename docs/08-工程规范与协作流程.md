## 1. 仓库结构约定

```
ordo/
├── README.md                 # 5 分钟上手
├── settings.gradle.kts       # 模块注册(条件化启用 Android/Windows)
├── build.gradle.kts          # 插件版本统一声明(apply false)
├── gradle/libs.versions.toml # 版本目录:唯一的版本来源
├── docs/                     # 00–08 工程文档(契约以此为准)
├── shared/core/              # KMP 共享核心(业务唯一实现)
├── apps/android|ios|harmony|windows/   # 四端客户端
└── server/                   # TypeScript 同步后端
```

**目录所有权(写权限)**

| 目录 | 所有者 | 其他人 |
|---|---|---|
| `docs/03`、`docs/04`、`shared/core`、根构建文件 | 架构师 | 只读 |
| `server/**` | 后端 | 只读 |
| `apps/<平台>/**` | 该端工程师 | 只读 |
| `docs/00–02,05–08` | 架构师(各端可提修改建议) | 只读 |

跨目录修改必须由架构师在集成阶段执行;任何"顺手改别人代码"都会导致契约漂移。

## 2. 分支与提交

**分支模型**:主干 `main` 始终可构建;特性分支短生命周期(≤3 天)。

```
main ──●────────●──────────●────────●──►
        \      /  \       /  \      /
         feat/…    fix/…     chore/…
```

| 分支前缀 | 用途 |
|---|---|
| `feat/<scope>-<desc>` | 新功能,如 `feat/android-schedule-sheet` |
| `fix/<scope>-<desc>` | 缺陷修复 |
| `chore/<desc>` | 构建、文档、依赖 |
| `contract/<desc>` | 契约变更(必须由架构师评审) |

**提交信息(Conventional Commits)**

```
<type>(<scope>): <subject>

<body:为什么这么改,而不是改了什么>

Refs: <契约条款/需求 ID>
```

示例:`feat(core): 支持 afterCompletion 重复模式\n\nRefs: docs/03 §6, PRD F-16`

**合并要求**:①自检通过 ②契约一致性检查表已勾选 ③不引入未声明依赖 ④改动范围与本工作包一致。

## 3. 代码规范

| 语言 | 规范 |
|---|---|
| Kotlin | 官方风格(`kotlin.code.style=official`);4 空格缩进;公共 API 必须写 KDoc;禁止 `!!`(除非有紧邻的非空断言且注释说明);实体属性若与关键字冲突用反引号(如 `` `when` ``) |
| Swift | Swift API Design Guidelines;开启 Swift 6 并发检查;`@MainActor` 标注 UI 状态;禁止 `fatalError` 占位 |
| ArkTS | 强类型:禁止 `any`、禁止动态属性;必须显式类型标注;`@Observed/@State/@Prop/@Link` 明确数据流方向 |
| TypeScript | `strict: true`;禁止 `any`(用 `unknown` + zod 校验);所有外部输入先过 schema |
| 通用 | 命名:类/类型 PascalCase、函数与变量 camelCase、常量 UPPER_SNAKE;中文文案集中管理(资源文件或常量表),禁止散落硬编码 |

**注释原则**:解释"为什么",不复述"做了什么";契约相关代码必须引用条款,如 `// 契约 §7.3.2 完成不可回滚`。

## 4. 依赖管理

1. 所有版本集中在 `gradle/libs.versions.toml`(Kotlin 侧)或 `server/package.json`(TS 侧)。
2. 新增依赖需说明:用途、许可证、体积、替代方案。
3. 禁止:GPL/AGPL 依赖、来源不明的二进制、运行时动态下载代码。
4. 升级依赖必须一次性同步四端(共享核心升级会同时影响 Android/iOS/Windows)。

## 5. 构建与验证(CI 目标形态)

| 阶段 | 命令 | 运行环境 |
|---|---|---|
| 核心测试 | `gradle :shared:core:jvmTest` | 任意(需 JDK 21) |
| 桌面端构建 | `gradle :apps:windows:build` | 任意(需 JDK 21) |
| 后端测试 | `pnpm -C server install && pnpm -C server test` | 任意(需 Node 20+) |
| Android 构建 | `gradle :apps:android:app:assembleDebug` | 需 Android SDK |
| iOS 构建 | `gradle :shared:core:assembleXCFramework` + `xcodebuild` | 仅 macOS |
| 鸿蒙构建 | DevEco `hvigorw assembleHap` | 需 DevEco Studio |

**合并前必跑**:与改动相关的行;**发布前必跑**:全部行。

## 6. 评审清单(PR Review Checklist)

- [ ] 契约一致性:字段名/枚举值/错误码/路由与 `docs/03`、`docs/04` 一致
- [ ] 测试:新增逻辑有对应用例;边界(空、超长、并发、断网)已覆盖
- [ ] 错误处理:失败路径有用户可理解的提示,且不丢数据
- [ ] 性能:大列表/高频操作无 O(n²) 与内存泄漏
- [ ] 无障碍:新增交互元素有可读标签
- [ ] 中文文案:统一、无错别字、无半角标点混排
- [ ] 无调试代码:无 `println`/`console.log` 残留、无 TODO 占位
- [ ] 范围:改动只落在本工作包目录

## 7. 版本与发布

**语义化版本**:`MAJOR.MINOR.PATCH`;契约变更 → 至少 MINOR;破坏性协议变更 → MAJOR 并同步 `schemaVersion`。

| 产物 | 版本来源 |
|---|---|
| Android | `versionName` / `versionCode`(build.gradle.kts) |
| iOS | `MARKETING_VERSION` / `CURRENT_PROJECT_VERSION` |
| 鸿蒙 | `app.json5` 的 `versionName` / `versionCode` |
| Windows | `nativeDistributions.packageVersion` |
| 后端 | `package.json` + `/v1/health` 返回 |

**发布流程**:冻结分支 → 全量测试 → 变更日志 → 灰度(Android 分阶段、iOS TestFlight、鸿蒙分阶段、Windows 直发)→ 全量 → 打 tag。

## 8. 缺陷与需求流转

```
发现 → 登记(docs/05 缺陷表或需求追踪矩阵) → 定级 → 排期 → 修复 → 回归 → 关闭
```

- 阻断级缺陷:立即停止其它工作,修复后由架构师复核。
- 需求变更:先改 `docs/01`(PRD)与 `docs/03`(契约),再改代码。
- 每次迭代结束更新 `docs/06` 的里程碑实测记录。

## 9. 文档规范

- 每份文档头部有"版本 / 日期 / 关联文档"表格,尾部有"变更记录"表。
- 契约类文档(03/04)变更必须在变更记录中写明影响端。
- 图表用 ASCII/表格表达,保证纯文本可读(便于 diff)。
- 文档与代码冲突时:**以文档为准,代码修**;若确需以代码为准,必须当天回填文档。
