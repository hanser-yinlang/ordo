**黑盒端到端覆盖的 25 项断言**(第三方视角,只认 HTTP 行为):

| 阶段 | 断言 |
|---|---|
| 请求验证码 | 202 + `sent/expiresIn=300/retryAfter=60`;开发模式回显 `devCode` |
| 同邮箱限流 | 60s 内重复请求 → 429 `RATE_LIMITED` + `details.reason=code_throttled` + `details.retryAfterSec∈[1,60]` |
| 错码 / 超次 | 错码一次 → 401 `code_invalid`;**连错 5 次 → `code_attempts_exceeded`,且之后连正确码也不放行** |
| 登录与同构 | 200;键集合 `user,device,accessToken,refreshToken,expiresIn` 与 register **逐字一致**;未注册邮箱自动建号(`email` 回显、`isGuest=false`) |
| 一次性消费 | 同一验证码二次使用被拒 |
| 无口令账号 | 走口令登录 → 401 `AUTH_INVALID_CREDENTIALS` |
| 数据隔离 | A push 后能拉到自己的待办;B(另一验证码账号)**看不到 A 的数据** |
| 既有账号 | 先注册带口令的账号 → 验证码登录**仍是同一 userId** → **原口令仍可用** |
| 参数校验 | 非法邮箱 / 非 6 位数字码 → 400 `VALIDATION_FAILED` |
| 令牌 | accessToken 可打同步接口;refreshToken 可刷新且响应同构 |

这正是 v1.6 加这条守卫(要求 `easing = OrdoEasing.transition` 出现 ≥4 次)的目的:防止"改了一处忘了另外三处"。补齐后 221 用例全绿。

**方法学收获(值得留档)**:v1.7 的曲线调整不是主观"再慢一点",而是把"不通畅"拆成了两个可验证的成因 ——
① 绝对时长不足以覆盖位移(180ms 跑 8px 看不出过程);② 贝塞尔曲线的**速度峰值位置**过早(前 1/3 完成大部分位移,后半段几乎静止,人眼读成"卡了一下")。
后者换曲线解决、前者加时长解决,两者共同构成"通畅"的手感。Windows 端的逐帧像素用例现在还额外钉住了首/末帧的上边缘差值,
等于把"位移过程真的铺开了"做成了回归项。
